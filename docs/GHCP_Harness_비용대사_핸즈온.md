# GHCP Harness 사내교육 핸즈온 — 월말 비용 대사

**v2 · 2026-08-26 · 3시간 · 사내교육 전용**

앞 판(`GHCP_Harness_비용처리_Agent_Workflow_핸즈온.md`)을 대신한다. 도메인은 그대로고 본류를 **단건 영수증 처리에서 월말 대사로** 옮겼다. 그 이유가 §1이다.

## 0. 이 문서를 읽는 법

**§1을 먼저 읽는다.** 나머지는 §1이 정한 것을 펼친 것이다.

문서 안의 문장은 세 종류다. 섞이지 않게 표시해 둔다.

| 표시 | 뜻 |
|---|---|
| (표시 없음) | 정해진 것. 이 문서가 결정한 사항이다 |
| `미확인` | 엔진에서 되는지 아직 확인하지 않았다. §9의 프로브가 정한다 |
| `잠정` | 정하긴 했으나 실측 전이다. 프로브 뒤에 다시 잡는다 |

**미확인을 §9 한 곳에 모아 두었다.** 본문에서 미확인이 걸리는 자리에는 프로브 번호를 붙인다.

## 1. 왜 이 업무인가

### 1.1 명분

> **가장 좋은 업무여서 고른 것이 아니다. Agent·Skill·Memory·Sandbox·Workflow가 전부 필요해지는 가장 작은 업무여서 골랐다.**

「최고인가」로 명분을 세우면 흔들린다. 최고에는 늘 상위 트림이 있고, 얼마 보태면 되는 것이 계속 보인다. 최소성은 두 방향 모두 한 문장으로 막힌다.

### 1.2 사다리

| | 무엇을 하나 | 결과 |
|---|---|---|
| 아래 | 영수증 한 장 → 문서 한 건 | **Sandbox가 죽는다.** OCR 결과 JSON이면 끝나서 파일을 열 이유가 없다 |
| **여기** | **명세 1,000행 + 증빙 대장 → 불일치 → 나머지 문서화** | **다섯 기능이 전부 강제된다. 완료 기준이 숫자로 떨어진다** |
| 위 | 여기 + ERP 연동 · 다국어 영수증 · 정책 예외 학습 | 기능은 이미 다 살아 있다. 붙는 것은 연동 설정과 실패 지점이다 |

아래로 내려가면 **이 교육의 존재 이유가 사라진다.** 단건 처리는 Copilot Studio로도 된다. 그러면 초급 과정과 무엇이 다른지 설명할 수 없다.

위로 올라가면 배우는 것이 엔진에서 연동 설정으로 바뀐다. 3시간에 들어가지 않고, 막힌 사람이 생기면 강사가 전원을 볼 수 없다. 설계할 때는 위쪽이 더 재미있다 — **복잡도의 비용은 설계자가 아니라 수강생이 낸다.**

### 1.3 기능마다 「없으면 안 되는 것」

이 표가 채워지지 않는 기능은 그 시나리오에서 장식이다. 다섯 칸이 다 찬다.

| 기능 | 없으면 안 되는 것 |
|---|---|
| Workflow | 사람이 파일을 열어 시작해야 한다 |
| Agent | 자료가 무엇이고 어떤 처리인지 사람이 매번 판단해야 한다 |
| Knowledge | 처리 기준을 사람이 규정집에서 찾아야 한다 |
| Skill | 결과 문서가 회사 양식으로 나오지 않는다 |
| Memory | 같은 것을 매번 다시 묻는다 |
| Sandbox | **1,000행 두 파일을 맞춰 볼 방법이 없다** |

### 1.4 흔들릴 때 대는 문장

**「이왕 하는 거 승인 워크플로까지 제대로 붙이자」**
승인은 §6에 이미 있다. 더 붙일 것은 기능이 아니라 커넥터 설정이고, 시간이 밀리면 가장 먼저 잘릴 자리다. 잘릴 것을 본류에 두지 않는다.

**「영수증 한 장으로도 다 보여줄 수 있지 않나」**
그러면 Sandbox가 왜 필요한지 말할 수 없다. Sandbox를 뺀 GHCP Harness는 초급 과정의 반복이다.

**「더 그럴듯한 업무가 있지 않나」**
있다. 다만 §1.3의 표가 다 차는 것 중 이보다 작은 것이 없다. 더 그럴듯한 것은 전부 위쪽 트림이다.

### 1.5 이 명분이 깨지는 조건

미리 정해 둔다. 아래가 나오면 시나리오를 되돌린다. **그 밖의 결과로는 되돌리지 않는다.**

- **프로브 1이 실패한다** — Sandbox가 업로드된 xlsx를 직접 열지 못한다. 그러면 §1.3의 마지막 칸이 비고 명분이 무너진다
- **프로브 2가 실패한다** — 결과 파일을 만들어 내려주지 못한다. 그러면 Skill이 양식 맞추기 이상을 못 한다

나머지 프로브는 명분이 아니라 **분량**을 정한다. Memory가 안 되면 Lab 3을 빼고, Workflow가 안 되면 Lab 4를 뺀다. 시나리오는 그대로 간다.

## 3. 전제 — GHCP에는 Topic이 없다

사용자의 질문을 미리 Topic으로 분기시키는 방식이 아니다. Agent가 입력과 자료를 보고 **무슨 일인지 판단**한다.

비용 처리 자료는 여러 형태로 들어온다 — 법인카드 명세, 증빙 대장, 영수증, 지출결의서, 경비정산서. 그래서 Agent가 먼저 답해야 하는 것은 이것이다.

> **이 자료가 무엇이고, 어떤 비용 처리 업무에 해당하는가.**

초급 과정(Copilot Studio)과 갈리는 자리이기도 하다. 거기서는 트리거 문구와 토픽으로 길을 정해 두었다. 여기서는 정해 두지 않는다.

## 4. 시나리오

> **"월말 법인카드 정산을 맡길 AI 담당자를 만들어 보자."**

한별소프트 경리팀의 월말 업무다. 초급 과정과 같은 가상 회사를 쓴다.

카드사에서 내려받은 **명세 1,000행**과 직원들이 올린 **증빙 대장 997행**을 맞춰 본다. 숫자가 다르므로 어딘가 어긋나 있다. 어긋난 것을 찾아 목록으로 만들고, 맞는 것은 처리 문서로 넘긴다.

### 4.1 이 에이전트가 어디에 붙나

**복리후생 에이전트의 에스컬레이션 대상이다.** 오늘 만드는 것을 따로 떨어진 물건으로 두지 않는다.

초급·중급에서 만든 복리후생 에이전트는 규정을 읽고 문답한다. 「자기계발비 한도가 얼마인가」에는
답하되, 「7월 카드값이랑 증빙이 안 맞는데 봐 달라」에는 답하지 못한다. **파일 두 개를 열어
1,000행을 맞춰 보는 일이기 때문이다.** 그 자리에서 넘겨받는 것이 오늘의 `비용 처리 담당` 이다.

| | 복리후생 에이전트 (표준 하네스) | `비용 처리 담당` (GHCP 하네스) |
|---|---|---|
| 무엇을 받나 | 규정 문답 | 파일 · 대사 요청 |
| 무엇으로 답하나 | Knowledge | Knowledge + **Sandbox 에서 연 파일** |
| 못 하는 것 | 1,000행 대사 | 상시 문답 — 크레딧이 나간다 |

**Lab 4의 분류가 그 자리를 실물로 만든다.** 평문으로 들어온 요청을 갈래로 갈라, 규정 문답은
M365 Copilot 이 받고 대사는 이 에이전트로 보낸다. 초·중급에서 만든 것과 오늘 만든 것이
한 워크플로 안에서 만나는 자리다.

⚠️ **시나리오는 비용대사 그대로다.** 복리후생을 본류로 올리지 않는다 — 올리면 Sandbox 가
죽고 §1.2의 사다리에서 한 칸 내려간다.

### 재료 (준비물)

**만들어야 한다.** 실제 카드 명세와 영수증은 쓸 수 없다.

| 파일 | 내용 |
|---|---|
| `카드내역_2026-07.xlsx` | 1,000행. 승인일자 · 가맹점 · 금액 · 카드번호 뒤 4자리 · 사용자 |
| `증빙대장_2026-07.xlsx` | 997행. 승인일자 · 가맹점 · 금액 · 제출자 · 증빙파일명 |
| `비용처리규정.md` | Knowledge 로 올릴 처리 기준 |
| `비용처리_표준양식.docx` | Skill 이 쓸 회사 표준 템플릿 |

**심어 두는 불일치는 3건이다.**

1. 증빙 누락 1건 — 명세에는 있고 대장에는 없다
2. 금액 불일치 1건 — 같은 건인데 금액이 다르다
3. 중복 증빙 1건 — 대장에 같은 건이 두 번 올라가 있다

1,000 − 997 = 3 이 그대로 답이 되지 않게 배치한다. 누락 1 · 중복 1이 상쇄되면 행 수 차이만으로는 못 찾는다. **행 수를 세는 것과 대사를 하는 것이 다르다는 것이 이 배치로 드러난다.**

## 5. Agent 설계

### 5.1 Agent가 수행할 업무

1. 들어온 파일이 무엇인지 확인한다
2. 어떤 비용 처리 업무인지 판단한다
3. 규정과 처리 기준을 확인한다
4. 두 파일을 대사한다
5. 불일치를 유형별로 분류한다
6. 판단이 서지 않는 것은 사용자에게 되묻는다
7. 결과 문서를 회사 양식으로 만든다
8. 만든 문서를 스스로 검증한다
9. 처리 결과를 반환한다

### 5.2 Knowledge — 회사가 알고 있어야 하는 것

- 비용 처리 규정
- 비용 유형별 처리 기준
- 증빙 기준
- 승인 기준
- 비용 코드 · 프로젝트 코드 기준
- 문서 유형별 작성 기준

판정 기준은 하나다.

> **Knowledge = 회사가 알고 있어야 하는 것.**

「법인카드 비용은 법인카드 내역서를 기준으로 처리한다」는 회사의 규칙이므로 Knowledge다.

### 5.3 Skill — 업무를 수행하는 방법

`expense-reconcile/SKILL.md`

```markdown
# Expense Reconciliation

## Purpose

법인카드 명세와 증빙 대장을 대사하여 불일치를 찾고,
회사 표준 양식의 정산 문서를 작성한다.

## Procedure

1. 두 파일을 승인일자·가맹점·금액으로 맞춘다.
2. 맞지 않는 건을 세 유형으로 나눈다 — 증빙 누락 · 금액 불일치 · 중복 증빙.
3. 유형별 건수와 금액 합계를 낸다.
4. 프로젝트 비용이면 프로젝트 코드를 확인한다.
5. 회사 표준 템플릿을 사용한다.
6. 결과 문서에 회사 워터마크를 삽입한다.
7. 작성된 문서의 필수 항목과 합계를 검증한다.

## Output

불일치 목록과 정산 문서를 생성한다.
```

**Skill 을 붙이기 전과 후의 결과물을 비교한다.** 기능 설명이 아니라 차이를 보게 한다.

| | 결과 |
|---|---|
| Skill 없이 | 일반적인 요약 문서 |
| Skill 적용 | 회사 표준 템플릿 + 워터마크 + 정해진 항목 순서 |

> **Skill = 「무엇을 하라」가 아니라 「이 일을 이런 방식으로 수행하라」.**

### 5.4 Memory — 이 사용자에게 지속되는 맥락

회사 규정은 Memory 에 넣지 않는다. 그건 Knowledge 의 영역이다.

Memory 에는 **사용자별로 반복되는 업무 맥락과 선호**를 넣는다.

| | 문장 |
|---|---|
| Knowledge | 프로젝트 비용에는 프로젝트 코드가 필요하다 |
| Memory | 이 사용자는 프로젝트 코드를 먼저 확인받기를 선호한다 |

성공 기준은 길지 않다. 세 단계가 돌면 충분하다.

> **기억한다 → 다음 업무에서 활용한다 → 필요한 정보를 먼저 되묻는다.**

### 5.5 Sandbox — 파일을 실제로 다루는 자리

- xlsx 두 개 읽기
- 1,000행 대사
- 템플릿 문서 처리
- 결과 문서 생성
- 워터마크 삽입
- 생성된 문서 검증

`미확인` 프로브 1·2·3

**전체를 읽었는지 판정하는 방법을 정해 둔다.** 명세 하단 합계와 Agent 가 낸 합계를 대조한다. 일부만 읽었다면 합계가 작게 나온다.

> **읽어 온 양은 물어봐서 아는 것이 아니라 합계를 맞춰 봐서 안다.**

#### 대조군 — 초급 과정에서 나온 값

`docs/appendix/read-volume.md` 의 실측이다. **다른 엔진(Copilot Studio + Excel Online 커넥터)의 값이므로 GHCP 에 그대로 적용되지 않는다.** 프로브 1·3의 결과가 나오면 그 값이 이 자리에 들어간다.

- 1,000행 표를 붙이면 배열이 `SD-0256` 에서 닫힌다. 커넥터가 기본 256행만 돌려준다
- 답변에는 「총 256건」이라고 적힌다. 물으면 한도를 밝히지만 먼저 말하지 않는다
- **1,000이라는 숫자는 끝내 나오지 않는다.** 얼마나 빠졌는지는 아무도 모른다
- 원시 출력은 23,723 토큰이었다

이 대조가 성립하면 교육 메시지가 선다.

> **실행 환경을 바꾸면 처리할 수 있는 자원의 범위가 달라지고, 그만큼 비용도 달라진다.**

성립하지 않아도 Lab 1의 대사는 남는다. 두 파일 대사는 어느 쪽이든 Sandbox 없이 안 된다.

```text

│   └── 회사 비용 처리 규정
├── Skills

├── Tools
└── Sandbox
    ├── xlsx 대사
    ├── 문서 생성
    └── 문서 검증
```

## 6. Workflow 설계

Workflow 는 프로세스를 통제한다. 판단과 문서 작업은 Agent 에게 위임한다.

```text
OneDrive 특정 폴더
        │
        │ 파일 추가
        ▼
Workflow Trigger
        │
        ▼
   파일 유형 판단
   ┌────┴──────────┐
   │               │
 대사 대상 2종     그 외
   │               │
   ▼               ▼
Agent 호출        Teams
   │              Fallback
   │              메시지
   │ 파일 2개
   ▼
비용 대사 Agent
   │
   ▼
Agent 결과 / Feedback
   │
   ▼
승인 처리
   │
   ▼
비용 처리 부서 이관
```

### 6.1 나누는 기준

| Workflow | Agent |
|---|---|
| 파일 추가 Trigger | 자료 이해 |
| 파일 유형 분기 | 대사와 불일치 분류 |
| Agent 호출 | 규정에 따른 검토 |
| Agent 결과 수신 | 필요한 정보 판단 |
| 승인 단계 연결 | 사용자에게 추가 질문 |
| 부서 이관 | 결과 문서 작성 |
| 예외 상황 처리 | 결과에 대한 판단 |

> **Workflow = 언제 시작하고, 어떤 순서로 진행하며, 결과에 따라 어디로 갈지를 통제한다.**
>
> **Agent = 프로세스 안에서 판단하고 일을 수행한다.**

### 6.2 Agent 에게 넘기는 것

파일 두 개를 함께 넘긴다. 구조화된 요약만 넘기지 않는다.

- `카드내역_2026-07.xlsx`
- `증빙대장_2026-07.xlsx`

**요약본만 넘기면 대사를 할 수 없다.** 원본이 있어야 어긋난 자리를 짚는다. 이것이 §1.3의 Sandbox 칸과 같은 이야기다.

### 6.3 OCR 은 본류에 두지 않는다

앞 판은 영수증 이미지를 OCR 로 읽는 것에서 시작했다. 이번 판에서는 뺐다.

OCR 은 **갈아 끼울 수 있는 부품**이다. 외부 API 를 붙이면 되고, 어느 것을 쓸지는 품질을 보고 정하는 문제다. 부품이 본류에 있으면 그 선택이 교육 전체를 흔든다.

붙일 자리는 남겨 둔다 — 증빙 대장 대신 영수증 이미지 묶음이 들어오는 경우가 그 자리다. **부록으로 둔다.**

### 6.4 Fallback

대사 대상이 아닌 파일이 들어오면 Agent 에게 넘기지 않는다.

```text
파일
 │
유형 판단
 ├─ 대사 대상 → Agent
 └─ 그 외      → Teams Fallback
```

Teams 메시지 예시.

> 대사 대상 파일로 식별되지 않았습니다.
> 카드 명세와 증빙 대장을 함께 올려 주세요.

> **AI 가 모든 것을 자동화해야 하는 것은 아니다.**

확실한 업무는 자동 처리하고 예외·불확실·잘못된 입력은 사람에게 돌린다.

### 6.5 Agent → Workflow 피드백

```text
Agent
 ├── 처리 가능      → 승인 처리 → 부서 이관
 ├── 추가 정보 필요 → 사용자 응답 → 재처리
 └── 처리 불가      → 담당자에게 전달
```

## 7. 랩별 실습과 완료 기준

완료 기준은 참가자가 **스스로 판정할 수 있는 형태**로 적는다.

### Lab 1 — Agent (40분) — 본류

| | 실습 | 완료 기준 |
|---|---|---|
| 1 | 에이전트 생성 · 이름 | Agent 가 응답한다 |
| 2 | **모델을 `Claude Sonnet 5` 로 고정** | 오른쪽 Model 이 Sonnet 5 다 |
| 3 | 업무 정의(지침) 작성 | — |
| 4 | Knowledge 에 비용 처리 규정 연결 | 규정에 있는 항목을 물으면 **규정 문장을 근거로** 답한다 |
| 5 | 규정에 없는 것을 물어본다 | 지어내지 않고 확인이 필요하다고 답한다 |
| 6 | **Sandbox 구조를 묻는다** | `/app` 아래에 무엇이 있는지 **스스로 열어** 답한다 |
| 7 | 파일 두 개를 첨부하고 무엇인지 묻는다 | **명세와 대장을 각각 무엇인지 구분해** 답한다 |
| 8 | 1,000행 전체를 읽었는지 확인한다 | **합계가 `100,849,600` 과 같다** |
| 9 | 불일치를 찾게 한다 | **유형별로 나온다** — 증빙 누락 1 · 금액 불일치 1 · 중복 1 |

**3번의 지침 한 줄이 6번을 가능하게 한다.** 교육 단계에서는 내부 구조를 설명하라고
지침에 적어 둔다. 적지 않으면 결과만 내놓고 어떻게 했는지는 말하지 않는다.

```
지금은 교육 단계입니다. 파일을 다룰 때는 결과만 내지 말고,
어떤 도구로 무엇을 열어 어떻게 처리했는지 함께 설명합니다.
```

9번의 완료 기준을 「3건」이 아니라 유형별로 적는다. **증빙 면제 3건이 따로 나오기 때문이다** —
실측에서 Agent 가 면제와 불일치를 갈라 냈다. 「3건」으로만 적으면 면제를 센 사람이 통과한다.

| 무엇 | 값 |
|---|---|
| 명세 하단 합계 | `100,849,600` |
| 대장 행 수 | 997 (머리글 포함 998행) |
| 면제 | 3건 · 553,100 (MS365 · Adobe · Slack) |
| 증빙 누락 | 1건 · 본죽 삼성점 76,500 |
| 금액 불일치 | 1건 · 한솥도시락 34,500 / 43,500 |
| 중복 | 1건 · 오피스디포 56,600 (RC-202607-0162 · 0163) |

9번의 끝에서 **결과가 나오되 양식이 사람마다 다른 것**을 눈으로 본다. Lab 2로 넘기는 자리다.

### Lab 2 — Skill (35분) — 본류

| | 실습 | 완료 기준 |
|---|---|---|
| 1 | **이미 갖고 있는 Skill 을 물어본다** | 내장 Skill 을 스스로 열거한다 |
| 2 | Skill 없이 대사 결과를 문서로 시킨다 | 결과가 나오되 양식이 제각각이다 |
| 3 | `expense-reconcile/SKILL.md` 작성 | — |
| 4 | **Skill 이 쓸 자료를 함께 싼다** | 템플릿이 Skill 묶음 안에 같이 들어간다 |
| 5 | Skill 을 에이전트에 붙이고 같은 요청을 다시 한다 | **2번과 결과 문서의 구조가 다르다** |
| 6 | 표준 양식으로 문서 생성 — `docx` | 문서 파일이 만들어져 내려받아진다 |
| 7 | 같은 것을 `pdf` 로 낸다 | **Skill 을 고치지 않고 형식만 바뀐다** |
| 8 | Skill 을 하나 더 붙인다 | 요청에 따라 다른 Skill 이 걸린다 |

**2번과 5번이 이 랩의 측정이다.** 같은 입력 · 같은 Agent · 같은 모델에서 Skill 만 다르다.

1번을 앞에 둔 이유가 있다. **Skill 은 새로 배우는 개념이 아니라 이미 돌고 있는 것이다.**
내장 Skill 을 스스로 열거하는 화면이 그 설명을 대신한다.

4번에 실을 자료와 8번의 두 번째 Skill 은 **아직 무엇으로 할지 정하지 않았다**(§13).

### Lab 3 — Memory 와 게시 (25분)

| | 실습 | 완료 기준 |
|---|---|---|
| 1 | 아래 문장을 그대로 입력한다 | — |
| 2 | Memory 에 저장되는지 확인 | 저장된 항목이 보인다 |
| 3 | 새 대화에서 새 대사를 요청한다 | **프로젝트 코드를 먼저 되묻는다** |
| 4 | 에이전트 화면을 훑는다 | 지식 · 도구 · 스킬 · 메모리 · 평가가 각각 무엇을 담는 자리인지 말할 수 있다 |
| 5 | 게시한다 | 게시 상태가 된다 |
| 6 | Teams 또는 M365 Copilot 에서 부른다 | **만든 에이전트가 밖에서 답한다** |

1번에 쓰는 문장을 고정한다. 사람마다 다른 문장을 쓰면 결과가 갈려 완료 판정이 되지 않는다.

```
법인카드 비용을 처리할 때 프로젝트 비용이면 프로젝트 코드를 먼저 확인해줘.
```

3번에서 기대하는 되물음.

```
이번 건은 프로젝트 비용으로 분류될 가능성이 있습니다.
프로젝트 코드를 알려주시겠어요?
```

**Memory 만으로는 랩 하나가 서지 않는다.** 4번과 5·6번이 그 분량을 받는다.
4번은 화면 투어이고, 5·6번은 만든 것을 밖으로 꺼내는 자리다.

⚠️ **모니터는 다루지 않는다.** 게시 뒤 집계까지 딜레이가 있어 3시간 안에 판정이 서지 않는다.
어디서 보는지만 말로 짚는다.

### Lab 4 — Workflow (50분)

**통으로 하나다.** 어제 직접 만들어 본 결과 연결 객체 문제는 CS 표준 하네스 교육을 거친
수강생에게 걸림돌이 아니었다. 쪼갤 이유가 없다.

| | 실습 | 완료 기준 |
|---|---|---|
| 1 | 만들어 둔 에이전트를 쓸 수 있는지 확인 | 에이전트 노드 목록에 뜬다 |
| 2 | 트리거를 잡는다 | 넣으면 실행 기록이 남는다 |
| 3 | **분류(Classify) — 평문을 갈래로 가른다** | 조건문이 볼 필드가 없는 글이 갈래로 간다 |
| 4 | **에이전트 노드** — 대사 갈래를 `비용 처리 담당` 으로 | 대사 결과가 돌아온다 |
| 5 | **M365 Copilot 노드** — 사내 자료로 답하는 갈래 | 답이 돌아온다 |
| 6 | 말단 노드를 붙인다 | 결과가 사람에게 도착한다 |
| 7 | 관계없는 것 → Fallback | **관계없는 글을 넣으면 메시지가 온다** |

**3번이 이 랩의 축이다.** If/Else 로 되돌리면 랩이 성립은 하되 배울 것이 없다 —
분류의 값은 조건문이 볼 필드가 없는 평문을 가른다는 데 있다.

**7번을 반드시 시킨다.** 자동화가 잘 도는 것보다, 안 되는 것을 사람에게 돌리는 자리를
직접 만들어 보는 편이 실무에서 오래 남는다.

#### 말단 노드 — 후보와 판단

**Outlook 보다 Teams 를 앞에 둔다.** E3 이라 메일이 되기는 하나 실제로 Outlook 을
안 쓰는 사람이 많다. 도착한 것을 확인하지 못하면 완료 판정이 서지 않는다.

| 후보 | 무엇 | 상태 |
|---|---|---|
| **Teams 메시지** | 갈래별 결과를 사람에게 보낸다 | **1순위.** 사용자 이름 게시인지 봇 게시인지 미확인 |
| **Excel 행 쓰기** | 처리 결과를 대장에 한 줄 남긴다 | 후보. 남는 것이 눈에 보인다 |
| 인적 검토 | 판단을 사람에게 넘긴다 | 필드는 실측으로 확인. **넣을지 미정** |
| Outlook 메일 | 승인 요청을 메일로 | 후순위 |

#### 초·중급 교육과의 비교

**여기가 비교군을 세우는 자리다.** 같은 수강생이 Copilot Studio 입문·중급에서 만든 것과
오늘 만든 것이 무엇이 다른지 말로 짚는다.

| | 입문 · 중급 (표준 하네스) | 오늘 (GHCP 하네스) |
|---|---|---|
| 갈래를 어떻게 가르나 | 토픽과 조건 | **분류 노드가 평문을 읽는다** |
| 처리 단위 | 대화 한 턴 | 파일 전체 |
| 연결 객체 | 같다 | 같다 — **여기서 막히지 않는다** |
| 과금 | 라이선스 | **크레딧. 만들기 시작할 때부터** |

## 9. 프로브 원장

시나리오와 무관하다. 어느 시나리오를 골라도 같은 것을 묻는다.
**Workflow 쪽은 노드 단위로 쪼갠다** — 「Workflow 가 된다」로는 판정이 서지 않는다.

| # | 무엇 | 상태 | 근거 · 대응 |
|---|---|---|---|
| 1 | Sandbox 가 xlsx 1,000행을 직접 여는가 | **된다** | 대사 완주. `/app/workspace/match2.py` 로 pandas |
| 2 | 결과 파일을 만들어 내려주는가 | **부분** | `/app/created/` 산출물이 첨부로 반환(txt). **docx·pdf 미확인** |
| 3 | 사용량·비용이 관찰되는가 | **안 된다** | 화면·DOM·네트워크 어디에도 토큰 필드가 없다. **사용량 확인 스텝을 뺀다** |
| 4 | Skill 전후로 결과가 달라지는가 | **미측정** | Lab 2의 2번 ↔ 5번이 이 측정이 된다 |
| 5 | Memory 가 다음 대화에 미치는가 | **된다** | 표식 회수 성공. 2층 구조 확인 |
| 6a | **에이전트 노드** | **부분** | 노드는 있다. **게시된 에이전트만** 목록에 뜬다 |
| 6b | **인적 검토 노드** | **있다** | 연결 자동. 필드 전부 확인. 실행 미확인 |
| 6c | **M365 Copilot 노드** | **있다** | 팔레트 확인. **연결 없음** |
| 6d | **분류(Classify)** | **있다** | 3분기 기본, 늘릴 수 있다. **연결 없음** — 필드 미확인 |
| 6e | 트리거 | **확인** | 5종. 커넥터에 OneDrive · SharePoint · Teams · **Forms** |
| 6f | **분류·M365 Copilot 용 연결** | **없다** | 환경에 그 종류가 없다. **Lab 4의 관문** |
| 6h | **Forms 트리거** | **있다** | 연결 자동(`edu@`) · 양식 ID 로 지정 · **E3 포함** |
| 7 | **Teams 말단 노드의 발신 주체** | **미확인** | 사용자 이름인지 봇인지. Lab 4 6번의 문안이 여기 걸린다 |
| 8 | **Excel 행 쓰기 말단 노드** | **미확인** | 후보. 대장에 한 줄 남기는 모양 |

| 무엇 | 막힌 이유 | 푸는 법 |
|---|---|---|
| Lab 4의 분류 · M365 Copilot | 6f — 연결이 환경에 없다 | 연결을 만든다. 동의 화면이 뜬다 |

## 10. 환경 체크리스트

교육처에 요청할 때 이 목록을 그대로 쓴다. `미확인` 표시는 프로브 뒤에 확정한다.

추가 충전 정책은 아직 적지 않았다.

**고객사 테넌트에서 진행할 때는 캡을 먼저 확인한다.** 캡이 걸린 환경에서는 미리 보기 대화가
다음으로 끊긴다.

```
This environment is out of credits.
Error code: EnforcementUsageCredits
```

수강생 1인 완주 추정이 9,000이므로 **캡은 인원수로 잡는다.** 강사의 저작·리허설 몫은 그 위에
얹힌다.

{: .note }
2026-09-02에 포스코 테넌트의 1,000 캡에 걸려 교안 작업이 멈춘 적이 있다. 캡 동작을 확인하려고
걸어 둔 것이었고, 같은 환경에서 저작하다 캡을 먹었다. **캡을 실험 중인 환경에서 저작하지 않는다.**

## 11. 교육 메시지

| | |
|---|---|
| Agent | 무엇을 해야 하는지 판단하고 실제 업무를 수행한다 |
| Workflow | 언제 시작하고 어떤 순서로 진행하며 결과에 따라 어디로 갈지를 통제한다 |
| Knowledge | 회사가 알고 있어야 하는 것 |
| Skill | 업무를 수행하는 방법 |
| Memory | 사용자에게 지속적으로 적용되는 업무 맥락 |
| Sandbox | 파일과 데이터를 실제로 다루는 실행 공간 |

### 한 문장

> **파일 두 개를 OneDrive에 넣었을 뿐인데, AI가 자료를 이해하고 1,000행을 맞춰 보고 어긋난 3건을 찾아내고, 필요한 것을 사람에게 되묻고, 결과 문서를 만들고, 승인과 부서 이관까지 연결한다.**

참가자는 각 기능을 기능 설명으로 배우지 않는다. 하나의 업무를 구현하면서 **그 기능이 없으면 무엇이 막히는지**를 만난다.

## 12. 검토했고 하지 않기로 한 것

같은 논의가 다시 올라올 때 여기부터 본다.

| | 왜 하지 않나 |
|---|---|
| 영수증 한 장 처리를 본류로 | Sandbox 의 당위가 서지 않는다. Copilot Studio 로도 되는 일이다 |
| OCR 을 본류에 | 갈아 끼울 수 있는 부품이다. 품질을 보고 정할 문제라 본류에 두면 교육이 흔들린다. 부록으로 둔다 |
| 사내 교육 운영 시나리오 | 한 업무가 아니라 세 업무의 묶음이다. 기능마다 다른 일감이 붙어 이음매가 셋 생긴다 |
| 제안서 초안 시나리오 | 결과물의 완료 기준을 세울 수 없다. 판정이 안 되면 당위도 서지 않는다 |
| 라이선스 정산 대사 | 기능 강제는 같다. 소재를 아는 사람이 담당자뿐이라 설명 비용에서 진다 |
| ERP 연동 · 다국어 영수증 | 기능은 이미 다 강제되어 있다. 붙는 것은 연동 설정과 실패 지점이다 |
